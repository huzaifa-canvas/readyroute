BACKEND UPDATE · FOR MOBILE DEV

ReadyRoute — Mobile App API Changes

Two new backend behaviours the dispatcher mobile app must support: a double-booking warning when assigning a driver, and a required reason when cancelling a trip.

Before you start

Nothing about auth or the base URL changes. Every endpoint below is the same Sanctum Bearer-token API you already use, and every response keeps the standard envelope:

{ "status": true|false, "message": "…", "data": …, "errors": … }

Only two flows change: Assign Driver and Cancel Trip. Read requests are unaffected.

1 Driver Assign — double-booking warning

A driver should not be stacked onto two trips too close together. If the chosen driver already has another active trip (scheduled / en-route / in-progress — not completed or cancelled) whose pickup lands within 1 hour before → 2 hours after this pickup, the server refuses with HTTP 409 until you resend with force: true.

Endpoints affected (same rule on all three)

MethodEndpointNew field
POST/api/dispatcher/trips/{id}/assignforce (bool, optional)
POST/api/dispatcher/trips (create)force (bool, optional)
PUT/api/dispatcher/trips/{id} (update)force (bool, optional)

409 response when there is a clash

{
  "status": false,
  "message": "Ali already has #41 (John Doe) at Nov 2, 1:30 PM — 1 hour before this pickup.",
  "data": null,
  "errors": {
    "conflict": true,
    "can_force": true,
    "message": "Ali already has #41 (John Doe) at Nov 2, 1:30 PM — 1 hour before this pickup.",
    "conflicts": [
      {
        "id": 41,
        "reference": "#41",
        "passenger": "John Doe",
        "pickup_at": "2026-11-02T13:30:00+00:00",
        "pickup_label": "Nov 2, 1:30 PM",
        "relation": "1 hour before this pickup",
        "status": "scheduled"
      }
    ]
  }
}

What the app should do

  1. Call assign / create / update normally (no force).
  2. 200 / 201 → done, driver assigned.
  3. 409 → show a dialog using errors.message and the errors.conflicts list, with two buttons:
    • Force Assign → resend the same request with "force": true → now returns 200.
    • Change Driver → go back to the driver picker.

Force retry example

POST /api/dispatcher/trips/88/assign
{ "driver_id": 12, "force": true }
Keep separate from 422: the existing "driver does not work on that day" error is still HTTP 422 with the message under errors.driver_id. That is a hard stop (no force) — handle it the way you do today. Only 409 offers Force Assign.

2 Trip Cancel — reason is now required

A cancelled trip stays on the record, so cancelling must now carry a reason. The cancel endpoint rejects a request without one.

Endpoint

MethodEndpoint
POST/api/dispatcher/trips/{id}/cancel

Request body

FieldRules
cancellation_reasonrequired — one of the values below
cancellation_notestring, max 500 — required only when reason is other

Reason values (exact)

client_no_show client_cancelled driver_unavailable vehicle_issue weather_emergency duplicate_trip other

Do not hard-code the list. Fetch it from GET /api/dispatcher/trips/form-options, which now returns a cancellation_reasons array. Show a text box whenever the selected option has needs_note: true. 
GET /api/dispatcher/trips/form-options  →  data.cancellation_reasons
"cancellation_reasons": [
  { "value": "client_no_show",    "label": "Client No-Show",      "needs_note": false },
  { "value": "client_cancelled",  "label": "Client Cancelled",    "needs_note": false },
  { "value": "driver_unavailable","label": "Driver Unavailable",  "needs_note": false },
  { "value": "vehicle_issue",     "label": "Vehicle Issue",       "needs_note": false },
  { "value": "weather_emergency", "label": "Weather / Emergency", "needs_note": false },
  { "value": "duplicate_trip",    "label": "Duplicate Trip",      "needs_note": false },
  { "value": "other",             "label": "Other",               "needs_note": true  }
]

Cancel request examples

POST /api/dispatcher/trips/88/cancel
{ "cancellation_reason": "vehicle_issue" }

// "Other" must include a note:
{ "cancellation_reason": "other", "cancellation_note": "Road closed" }

200 → cancelled, updated trip returned in data.   422 → reason missing/invalid, show errors.

Showing the reason on a cancelled trip

Every trip object (TripResource) now includes these fields — display cancellation_reason_label on a cancelled trip's detail:

"cancellation_reason":       "vehicle_issue",
"cancellation_reason_label": "Vehicle Issue",   // for "Other" → "Other: Road closed"
"cancellation_note":         null

What the app should do

  1. On Cancel, show a reason picker (radio list from form-options) + a note box for the option whose needs_note is true.
  2. POST to /trips/{id}/cancel with cancellation_reason (and cancellation_note for "Other").
  3. 200 → cancelled, refresh. 422 → show the validation message.

Checklist

  • Handle 409 on assign / create / update → "Force Assign" + "Change Driver" dialog; retry with force: true.
  • Keep the existing 422 availability error (driver's day off) as a hard stop — no force.
  • Cancel screen: reason radios from form-options, plus a note box for "Other".
  • Send cancellation_reason (+ cancellation_note for "Other") on cancel, or you get 422.
  • Show cancellation_reason_label on cancelled-trip details.
Backend note (not the app's job): the server must have the new database migration applied. If you hit a 500 on cancel, the backend migration has not been run yet — tell the backend team.
